# مدیر سوپرگروه «گویندگان حرفه‌ای»

این بسته یک ربات Python بر پایه `python-telegram-bot` 22.8+ است. ربات با webhook در Render (وجود `PORT`) و با polling در اجرای محلی اجرا می‌شود. فقط یک نمونه polling باید فعال باشد. هیچ ارتباطی با تلگرام یا Render در این محیط واقعی آزمایش نشده است.

## امکانات پیاده‌سازی‌شده
- بررسی شناسه واقعی هر یک از ۹ موضوع، لینک/نام‌کاربری/فوروارد، فهرست واژه‌ها و اثرانگشت پیام متن/رسانه (Telegram file_unique_id) با نگهداری ۳۰روزه.
- شمارش نمونه‌کار هفتگی و ماهانه، معرفی ماهانه، شمارنده گفتگوی عمومی و سقف پادکست، ثبت تعرفه و ویرایش، همکاری خصوصی با تأیید مدیر، تخلفات persistent، پشتیبان JSON ماسک‌شده.
- فرمان‌های `/help`, `/status`, `/topic_id`, `/group_id`, `/warnings`, `/history`, `/set_topic`, `/unmute`, `/collab`, `/collabs`, `/approve`, `/reject`, `/backup`, `/restore`, `/reset_counter`.
- شروع درخواست همکاری در خصوصی با نام، تلفن و ایمیل؛ نام کاربری از Telegram ثبت می‌شود. اطلاعات فقط پس از تأیید مدیر منتشر می‌شود.
- بررسی واژه‌های ممنوعه در اولویت اول برای «هر» پیام غیرمدیریتی (متن یا کپشن) — حتی اگر تاپیک هنوز شناسایی نشده باشد؛ پیام فوراً حذف و تخلف با تشدید (تذکر → سکوت → ban) ثبت می‌شود.
- محدودیت سخت گفت‌وگوی عمومی برای کاربران معمولی: حداکثر `RATE_LIMIT_GENERAL_PER_HOUR` (پیش‌فرض ۱۰) پیام در هر ساعت؛ پیام مازاد حذف، تخلف ثبت و تنبیه مرحله‌ای اعمال می‌شود.
- اطلاع «شناسه‌های موضوع تنظیم نشده‌اند» فقط یک‌بار در هر اجرای ربات ارسال می‌شود و روی هر پیام تکرار نمی‌شود.

## محدودیت‌ها/رفتارهای محافظه‌کارانه
- شناسه‌های موضوع در `.env`/Render تنظیم شوند، نه حدس زده شوند. اگر شناسه ناقص باشد، محدودیت موضوعات شناسایی‌شده اعمال نمی‌شود. در هر تاپیک `/topic_id` و شناسه `message_thread_id` را ببینید؛ مقدار `message_thread_id` را برای متغیر موضوع مربوط ثبت کنید؛ آن را با `message_id` پیام عادی اشتباه نگیرید.
- فهرست لینک بدون سرویس بیرونی، دامنه‌ها، URL entity، `@username` و forward metadata را می‌بیند؛ لینک پنهان فقط در صورت Telegram entity قابل تشخیص است. تشخیص معنایی محتوای تخصصی یا بازنویسی/تصویر مشابه ادعا نمی‌شود.
- «پنج کاربر دیگر» برای گفتگوی عمومی تعریف شده: پنج کاربر متمایز که پس از آغاز پنجره فعال‌اند. کد شمارنده تجدید را با پنجره ساعت مطلق می‌سازد؛ این تقریب، سیاست دقیق نوبت‌محور را کاملاً مدل نمی‌کند. سهمیه روزانه مستقل است. پادکست سقف کل ۱۲ و سقف ۳/ساعت را دارد، اما شمارش پنج کاربر در نسخه فعلی با شمارش پیام‌های دیگران انجام شده، نه کاربران متمایز؛ این مورد نیازمند بازبینی/تأیید است.
- آلبوم تلگرام به صورت چند update می‌رسد؛ اثرانگشت هر پیام جداست، لذا گروهی از عکس‌های آلبوم به عنوان یک پست تجمیع نمی‌شود. شمارش نمونه‌کار هر پیام است.
- API تلگرام اجازه جلوگیری پیشینی از ارسال اعضا در موضوع پروژه‌ها/قوانین را نمی‌دهد؛ پیام بعد از دریافت حذف/مدیریت می‌شود و نیازمند مجوز Delete messages است. محتوای خارج از موضوع با واژه‌نامه ساده تشخیص‌پذیر نیست.
- تخلف‌ها با update_id یکتا هستند. هشدار سطح اول، سکوت ۲۴ساعته، سکوت ۷روزه و ban در چهارمین تخلف. ربات باید مجوز Restrict/Ban/Delete داشته باشد. مدیریت خطای API ثبت می‌شود؛ مدیران به طور پیش‌فرض تنبیه خودکار نمی‌شوند.
- پیام تعرفه‌ها در Telegram قابل قفل‌کردن نیست. این پیاده‌سازی فقط پیام اول/تغییرهای دریافتی را دنبال می‌کند و حذف و ارسال مجدد را با قطعیت به هم مرتبط نمی‌سازد. `/unmute` مجوزهای رایج را باز می‌کند؛ اگر قبلاً مجوزهای سفارشی بوده، تنظیم دقیق باید توسط مدیر انجام شود.
- `DB_PATH` پیش‌فرض Render روی فایل‌سیستم موقت است و اطلاعات با redeploy/تعویض نمونه ممکن است از بین بروند. ماندگاری تضمین نیست. برای نگهداری پایدار از دیسک در صورت ارائه/قیمت‌گذاری Render یا نسخه پشتیبان دستی استفاده کنید؛ امکانات رایگان میزبان تغییرپذیرند. SQLite یک فایل مشترک برای چند instance مناسب نیست.
- داده‌های همکاری خصوصی‌اند؛ `/backup` عمداً اطلاعات تماس درخواست‌ها را صادر نمی‌کند. فایل پشتیبان را در مخزن عمومی نگذارید. دوره پاک‌سازی اطلاعات قدیمی از طریق `Database.purge_collab_privacy` قابل فراخوانی است.
- region زمانی شمارش‌ها فعلاً UTC است (README: مقایسه ماه/روز با UTC؛ timezone config صرفاً مستند است). برای سیاست ماهانه تهران لازم است شمارش‌ها به `Asia/Tehran` منتقل شوند.

## موضوع‌ها و شناسه‌های قطعی
این نگاشت مطابق اطلاعات ارائه‌شده است؛ اعداد را حدس نزنید یا تغییر ندهید:

| متغیر Render | موضوع | شناسهٔ موضوع |
|---|---|---:|
| `TOPIC_1` | گفت‌وگوی عمومی گویندگان | `1` |
| `TOPIC_2` | پادکست؛ تولید و تدوین | `213` |
| `TOPIC_3` | قوانین و اطلاعیه‌ها | `14` |
| `TOPIC_4` | نمونه‌کارهای گویندگی | `3` |
| `TOPIC_5` | معرفی گویندگان حرفه‌ای | `66` |
| `TOPIC_6` | تعرفه‌ها و قراردادهای گویندگی | `72` |
| `TOPIC_7` | پروژه‌ها و درخواست‌های همکاری | `4` |
| `TOPIC_8` | نقد و بررسی کارهای گویندگی | `473` |
| `TOPIC_9` | ویرایش و بهینه‌سازی صدا | `488` |

در Telegram، `message_thread_id` در پیام واقع در forum topic شناسهٔ موضوعی است که این متغیرها می‌خواهند. `message_id` شناسهٔ یک پیام منفرد است و جایگزین `message_thread_id` نیست؛ `/topic_id` هر دو را جداگانه نشان می‌دهد. نگاشت بالا مقادیر شناسهٔ موضوعِ تأییدشده را مشخص می‌کند.

متغیر `RATE_LIMIT_GENERAL_PER_HOUR` در `.env.example` تعریف شده و مقدار پیش‌فرض آن ۱۰ است.

کلیدهای قدیمی معنایی (`TOPIC_GENERAL`، `TOPIC_PODCAST`، `TOPIC_RULES`، `TOPIC_PORTFOLIO`، `TOPIC_INTRO`، `TOPIC_TARIFF`، `TOPIC_PROJECTS`) برای سازگاری حفظ شده‌اند، اما فقط وقتی کلید شماره‌دار متناظر خالی باشد خوانده می‌شوند. از این پس در Render کلیدهای `TOPIC_1` تا `TOPIC_9` را تنظیم کنید.

## نصب و اجرای محلی
1. Python 3.11+ نصب و پوشه پروژه را دریافت کنید.
2. `python -m venv .venv` و فعال‌سازی محیط؛ سپس `pip install -r requirements.txt`.
3. `.env.example` را به `.env` کپی کنید. `BOT_TOKEN` واقعی BotFather و `OWNER_ID` عددی را وارد کنید. هیچ فایل `.env` را commit نکنید.
4. در گروه `/topic_id` را در تاپیک‌ها اجرا کنید و در صورت نیاز `message_thread_id` را برای شناسایی تطبیق دهید. مقادیر قطعی در جدول «موضوع‌ها و شناسه‌های قطعی» آمده‌اند.
5. `GROUP_ID` را از `/group_id` بگیرید؛ ربات را عضو supergroup کنید و ادمین با دسترسی Delete messages، Restrict members، Ban users و ارسال پیام در موضوعات کنید. برای دریافت پیام‌های عادی در BotFather privacy mode را خاموش کنید یا ربات را ادمین کنید.
6. اجرای محلی: `python main.py` (polling؛ در هر زمان فقط یک نمونه).

## استقرار Render با GitHub
1. در BotFather با `/newbot` ربات بسازید، توکن را محرمانه نگه دارید؛ اگر افشا شد از BotFather توکن را revoke و در Render جایگزین کنید.
2. فایل‌های همین پروژه را در یک مخزن GitHub جدید push کنید. پیش از commit وضعیت `.gitignore` را بررسی کنید؛ `.env` و فایل DB نباید بارگذاری شوند.
3. Render → New → Web Service → مخزن را انتخاب کنید. Runtime Python؛ Build: `pip install -r requirements.txt`; Start: `python main.py`.
4. متغیرها: `BOT_TOKEN`, `OWNER_ID`, `WEBHOOK_URL` (آدرس HTTPS سرویس مانند `https://نام.onrender.com`)، `WEBHOOK_SECRET` (رشته تصادفی امن)، `TOPIC_1` تا `TOPIC_9`، `GROUP_ID`، `RATE_LIMIT_GENERAL_PER_HOUR` (پیش‌فرض ۱۰؛ سقف پیام در ساعت در گفت‌وگوی عمومی) و در صورت نیاز `DB_PATH`. `render.yaml` حداقل متغیرهای اصلی را نشان می‌دهد. شناسه‌های نمونه `.env.example` را کپی نکنید.
5. Deploy و Logs را بررسی کنید. `WEBHOOK_URL` لازم است وقتی Render تزریق PORT کند. سپس در Telegram آزمایش کنید: `/status`, `/topic_id`, و قوانین، لینک و محدودیت‌ها. اگر privacy فعال باشد، ربات پیام‌های عادی را نمی‌بیند.
6. Render رایگان ممکن است سرویس را در بی‌کاری بخواباند، ظرفیت/ساعت یا منابع محدود کند و فایل‌سیستم ephemeral باشد؛ رفتار و قیمت پلن را هنگام استقرار بررسی کنید. polling روی Render برای Web Service مناسب نیست؛ webhook انتخاب شده است.

## پشتیبان و بازیابی
- مالک در گروه `/backup` می‌زند؛ JSON پیوست می‌شود (درخواست‌ها بدون اطلاعات تماس). آن را امن و خارج از GitHub نگه دارید.
- بازیابی: فایل JSON را به `/restore` در گروه پیوست کنید. به‌دلیل حساسیت، فقط `OWNER_ID` مجاز است. restore ادغام می‌کند؛ ابتدا فایل را بررسی کنید.
- درخواست همکاری بعد از دوره موردنظر: کد `purge_collab_privacy(ISO_TIMESTAMP)` شماره و ایمیل درخواست‌های رد/منتشرشده قدیمی را خالی می‌کند؛ پیش از پاک‌سازی نسخه امن تهیه کنید.

## تست‌ها
`pytest -q` اجرا کنید. تست محلی، API تلگرام/استقرار واقعی را پوشش نمی‌دهد. پس از deploy مالک باید دسترسی ادمین، ۹ شناسهٔ تاپیک، تنبیه آزمایشی، درخواست خصوصی، backup/restore و پایداری فایل DB را دستی تأیید کند.
